# xiaozhi-esp32-golang-server 架构设计指导

## 1. 架构目标与范围

### 1.1 系统范围

系统面向 `xiaozhi-esp32` 设备，提供设备生命周期管理、实时双向语音交互、Agent 运行方案管理，以及服务端和设备 MCP 工具协作能力。管理界面通过受控入口维护设备、AI 能力与工具配置。

本文描述系统上下文、逻辑职责、运行时协作、数据所有权和部署演进边界，不规定代码目录、类型与函数、数据库表字段、接口路径与报文、调度机制、具体参数或供应商选型，也不承担实现现状清单、运行手册和缺陷跟踪的职责。

### 1.2 架构目标

| 目标 | 架构要求 |
| --- | --- |
| 职责清晰 | 业务规则、会话控制、交互执行与外部能力分别拥有明确边界，不争夺状态和资源所有权。 |
| 变更隔离 | 管理配置变更不直接改写执行中的会话；供应商和基础设施变化不影响上层业务契约。 |
| 运行可控 | 执行具有明确的交付结果、资源预算、取消关系和故障退出边界。 |
| 安全隔离 | 设备、用户、管理者及外部服务的信任关系明确，能力调用不隐式扩大权限。 |
| 可演进 | 逻辑边界不绑定永久单体或单实例假设，允许根据实际需求演进部署方式。 |

### 1.3 设计约束

- 兼容设备既有协议；内部演进不得要求设备理解服务端模块、持久化结构或供应商差异。
- 逻辑职责不等同于代码包或部署单元；只为真实调用方和明确变化点建立抽象。
- 架构要求与实现保证分开表达。实现存在差距时，应识别差距，而不是据文档宣称能力完成或为迁就缺陷降低约束。

## 2. 系统上下文

```text
设备 ───── 配置发现、激活、语音与设备工具交互 ──┐
用户 ───── 设备绑定与用户操作 ───────────────┼── 服务端 ── 外部 AI 服务
管理者 ─── 管理界面与管理操作 ───────────────┘       ├── 外部工具服务
                                                   └── 持久化存储
```

图中连线表示系统与外部协作方的关系，不规定协议时序或部署方式。管理界面是交互边界，其交付方式不改变服务端的业务与授权责任。

| 协作方 | 服务端责任 | 边界约束 |
| --- | --- | --- |
| 设备 | 确认访问资格、组织交互、交付音频与控制意图、接纳设备工具结果 | 设备负责内部采集、播放及硬件执行；服务端写出不等于设备已完成动作。 |
| 用户与管理者 | 校验身份、资源归属和操作权限，提供相应业务能力 | 设备身份、用户身份和管理身份不能相互替代；界面不能替代服务端授权或直接访问持久化。 |
| 外部 AI 与工具服务 | 提供中立调用契约，约束权限、资源消耗及失败传播 | 外部服务不决定设备归属，不提升调用者权限，不直接修改会话状态。 |
| 持久化存储 | 保存设备关系与配置的权威记录，执行事务并协调数据演进 | 存储技术不定义业务资格；存储提交不代表结果已交付给设备。 |

## 3. 逻辑架构

### 3.1 职责划分

| 逻辑职责 | 主要责任 | 不拥有的责任 |
| --- | --- | --- |
| 接入适配 | 请求协议适配、输入校验、身份与权限检查，将请求交给对应业务边界 | 业务状态所有权和持久化细节 |
| 设备生命周期 | 设备身份、激活关系、用户归属与访问资格的业务规则 | 语音处理和会话输出 |
| 配置治理 | Agent 运行方案、设备类型映射、AI 与工具配置及引用有效性 | 执行中的会话与轮次状态 |
| 会话管理 | 准入、连接生命周期、轮次调度、历史提交及统一输出 | 供应商协议、音频算法和具体工具逻辑 |
| 语音轮次编排 | 协调本次识别、模型响应、工具协作、语音合成与音频处理，返回统一轮次结果 | 设备连接、会话历史提交和会话生命周期决策 |
| 工具能力 | 服务端与设备工具的描述、发现、受控执行及结果归一化 | 调用者权限和会话控制权 |
| AI 能力适配 | 提供识别、模型生成与工具调用循环、语音合成的中立能力，隔离供应商差异 | 设备业务规则和会话状态 |
| 音频处理 | 音频格式转换与连续音频流处理 | 模型语义、工具调度和业务状态判断 |
| 持久化边界 | 受控数据访问、事务执行、存储结构演进及底层连接管理 | 设备资格决策和会话运行状态 |
| 基础设施装配 | 依赖装配、实例启动与停止、诊断支撑 | 设备、对话和工具的业务规则 |

上述职责是逻辑边界，不要求逐项创建独立模块、接口或服务。

### 3.2 依赖关系

```text
接入适配
   ├──> 设备生命周期 ──> 持久化边界
   ├──> 配置治理     ──> 持久化边界
   └──> 会话管理
            ├──> 运行方案读取 ──> 持久化边界
            ├──> 语音轮次编排
            │         ├──> AI 能力适配 ──> 外部 AI 服务
            │         └──> 音频处理
            └──> 工具能力
                      ├──> 服务端工具
                      └──> 设备 MCP 工具
```

- 业务编排依赖中立能力，不依赖供应商协议、底层连接或持久化实体；配置进入运行时边界时转换为调用方需要的运行选项。
- 会话向轮次提供运行方案、工具能力和输出契约；轮次返回结果，不反向访问会话内部状态。
- 设备工具通过会话提供的最小通信契约使用连接，不取得连接所有权。
- 实时交互可以读取受控配置，但不通过管理界面或管理请求流程完成内部调用，也不与配置治理共享可变执行状态。
- 结果与控制意图向上返回，不构成直接操作上层状态的许可；模块依赖不得成环。

## 4. 运行时架构

### 4.1 生命周期与状态所有权

| 作用域 | 状态与资源 | 生命周期责任 |
| --- | --- | --- |
| 实例 | 本实例的基础设施资源、服务入口、持久化连接与准入能力 | 统一创建与释放；停止时关闭本实例的新准入，再清理其拥有的存量资源。 |
| 会话 | 设备连接、运行方案、会话历史、设备工具能力与轮次调度状态 | 决定交互秩序、接纳轮次结果、提交历史和关闭连接。 |
| 轮次 | 本次输入、工具集合、执行上下文、生成结果与控制意图 | 执行一次交互并返回终态；终止后不再影响后续轮次。 |

每项可变状态必须有唯一的权威所有者。取消沿所有权向下传递，结果和意图沿调用关系向上返回；父级终止必须结束其拥有的子任务，子任务不能越权控制父级或其他轮次。

### 4.2 主要交互流程

```text
设备接入 ──> 身份与访问资格确认 ──> 运行方案与通信能力确认 ──> 会话就绪

会话发起轮次 ──> 语音识别 ──> 模型与工具协作 ──> 语音合成与音频处理
                                                               │
                                                               ▼
会话接纳结果 <── 轮次终态 <── 交付确认 <──────────────────── 统一连接输出
```

此图表达阶段职责与结果归属，不规定阶段内部的流式处理、并行调度或报文格式。

- 网络连接成功不等于业务就绪；进入正式交互前必须确认必要访问资格、通信能力及运行方案。
- 所有音频与控制输出经过会话管理的统一输出边界，轮次和工具不得各自建立连接写入路径。
- 轮次成功以输出边界确认的交付结果为依据，不能用模型生成完成、任务提交或进入缓冲代替。
- 会话根据完成结果提交历史，保留后续交互所需的工具请求与结果关系；失败、取消和迟到结果不得留下影响后续交互的半完成记录。

### 4.3 工具执行与副作用

- 模型只能调用当前交互明确提供的工具；设备声明能力不自动取得服务端或用户权限，也不能覆盖服务端保留能力。
- 工具发现与调用不能阻断接收设备响应所依赖的会话控制路径。可选工具故障应限制在对应能力范围内。
- 工具结果、执行错误与会话控制意图分别表达。请求结束会话只产生意图，由会话在对应轮次成功交付后执行；轮次取消使该意图失效。
- 取消约束后续执行与结果接纳，不表示已经发生的外部或硬件动作被回滚。结果未知时，不得伪装成功或隐式重复执行。

## 5. 数据与配置架构

### 5.1 领域数据与权威来源

| 数据域 | 主要关系 | 权威边界 |
| --- | --- | --- |
| 设备生命周期 | 设备身份、激活状态、用户归属及访问凭据 | 持久化业务记录；身份合法、归属有效和凭据可用分别判断。 |
| Agent 运行方案 | 设备类型选择 Agent，Agent 组合识别、模型、合成及交互行为配置 | 配置治理负责必要引用与能力有效性；会话使用确定的运行方案。 |
| 工具配置与能力 | 服务端工具配置、设备提供的工具能力和轮次工具集合 | 配置治理管理服务端配置，设备能力归对应会话，执行集合归当前轮次。 |

临时缓存与连接状态不能形成另一套冲突的业务事实。会话历史属于交互上下文，不替代设备身份、归属或配置的权威记录。

### 5.2 一致性边界

- 激活、绑定、凭据签发及旧资格失效按业务不变量划定事务边界，避免部分提交破坏访问资格的一致性。
- 必要引用与能力可用性在管理写入和运行方案装配时均应校验，不以无关默认方案掩盖配置缺失。
- 持久化提交、网络交付与外部执行不是同一个原子操作，必须分别定义成功、失败和重试责任。
- 数据结构演进必须可审计，并与应用兼容范围协调。

### 5.3 配置生效范围

| 配置类别 | 生效范围 | 变更约束 |
| --- | --- | --- |
| 基础设施配置 | 实例 | 通过受控实例生命周期生效，不隐含所有实例同时变更。 |
| Agent 与 AI 运行方案 | 会话 | 建立时确定，管理更新不原地替换执行中的会话方案。 |
| 工具执行集合 | 轮次 | 执行期间固定，工具来源更新不得改写当前轮次集合，设备能力不得被其他会话继承。 |

允许新选择、运行时可用和既有引用有效是不同语义。限制新增引用与终止既有运行的策略必须分别定义，不能用一个含糊的启用概念替代。

## 6. 部署架构与演进

### 6.1 阶段性选择

| 阶段 | 架构定位 | 不作出的承诺 |
| --- | --- | --- |
| 近期 | 采用单体组织控制开发与运维复杂度，内部保持清晰的职责边界 | 不将单体或单实例固定为长期架构约束，也不据此认定跨实例协作已经具备。 |
| 长期演进 | 根据容量、可用性与运维需求保留多实例部署和水平扩展空间 | 不预设必须拆分服务，也不提前指定分布式协调方案。 |

单体描述代码与服务的组织方式，多实例描述部署方式，两者并不互斥；服务拆分是独立决策，不能以增加实例数量作为自动拆分的理由。

### 6.2 多实例边界

- 共享业务事实与实例内运行状态必须区分，不能依赖某个实例的本地状态维持全局业务正确性。
- 会话归属、临时状态可见性及设备互斥必须明确协调责任；活跃连接不默认具备跨实例迁移或故障接管能力。
- 实例内状态管理和资源预算不构成全局保证；需要全局约束时，必须单独明确其作用范围与责任方。
- 实例停止只清理该实例拥有的资源，不等同于全系统停止；配置生效和数据演进需要考虑实例间的兼容关系。

## 7. 安全与可靠性设计

### 7.1 安全边界

- **身份与授权**：设备、用户和管理者是不同信任主体；接入成功或模型提出工具调用均不构成额外授权。
- **敏感数据**：凭据写入、运行时使用、必要下发与普通查询展示分离；普通查询与常规管理展示不得返回秘密原文，凭据校验不得暴露可被利用的比较差异。
- **输入与诊断**：不可信输入在接入边界接受校验与资源限制；日志不能成为数据出口或资源耗尽通道，访问凭据、设备密钥和原始音频不得进入普通日志。
- **传输保护**：跨不可信网络的设备、管理及外部服务通信必须受安全传输保护；传输保护不能替代应用授权。

### 7.2 资源与故障隔离

- 会话并发、输入载荷、音频缓冲、历史、外部调用及工具迭代均必须有资源预算；初始化、执行、外部等待与清理均必须有超时或取消边界。
- 持续拥塞必须触发背压、拒绝或终止，不能依靠无界积压维持表面可用。
- 必要能力失败与可选能力失败具有不同传播范围；不可恢复的输出故障结束相关会话，可选能力失败不默认破坏基础语音交互。
- 资源创建、使用与释放具有明确责任方，成功、失败、取消和实例停止均不能留下无所有者的后台工作。
- 错误跨边界时转为调用者可处理的语义，不泄露底层协议与敏感内容。

## 9. 架构评审与维护

| 评审维度 | 设计证据 | 通过条件 |
| --- | --- | --- |
| 结构与依赖 | 职责说明与能力依赖图 | 主要业务路径责任明确，依赖无环，新增边界有真实调用方和隔离理由。 |
| 状态与协作 | 生命周期与交互流程图 | 状态所有者、结果接纳者及资源释放责任明确，取消与迟到结果不能跨作用域生效。 |
| 数据与配置 | 领域关系、一致性与配置生效说明 | 重试、并发和部分失败不破坏业务不变量，配置变更影响明确。 |
| 部署与演进 | 部署阶段与实例边界说明 | 实例内保证与全局约束分开，不隐含连接迁移、故障接管或全局互斥能力。 |
| 安全与可靠性 | 信任关系、敏感数据流、资源预算与故障传播说明 | 权限不因调用扩散，敏感数据无旁路出口，等待与积压具有退出边界。 |

完成标准是各架构视图相互一致，关键边界有明确设计依据，未决事项被显式保留，且架构要求与实现保证没有混写。

系统范围、职责、所有权或跨边界契约变化时更新本文，并检查人类概览是否需要同步；只改变边界内部实现时，不改变本文的架构承诺。
